# 校正済みTXTの読み込み

## 使い方

TXTの追加画面で「TXTの読み込み方式」から「校正済みTXT（段落・空白を保持）」を選択して登録する。先頭2行は作品名・著者名。空行で段落を区切る。空行がないTXTでは、非空行を1段落として扱う。空行で区切った段落内の改行・字下げ・英文の空白は保持する。

既定は「従来の整形（OCR・青空文庫）」のまま。既存登録の方式は自動変更しない。既に従来方式で登録した校正済みTXTは、新方式で別作品として再登録する必要があり、旧作品の読書位置やリアクションを自動移行しない。

## 実装

- `app/text-reading-format.ts`: `legacy` / `proofread-v1`の判定と校正済みTXT用パーサー。原文の文字を補正せず、Ⅰ〜Ⅶ等を文字列の変更なしに見出しにする。将来互換のため方式名をバージョン付きにし、未知値・未指定は従来方式へ戻す。
- `app/page.tsx`: 登録画面の方式選択、作品の`readingFormat`保存と読込時の分岐。既存の`textSource`は出典分類として維持し、既存OCR・青空文庫の`cleanAozoraText`は変更しない。校正済みTXTに限り文分割時のtrimを抑制し、横書き・縦書き・2文グループの各表示で`white-space: pre-wrap`を使用する。
- `app/group-work-sharing.ts`: 共有本文を個人ライブラリへ複製する際に`readingFormat`もコピー。同じworkIdを参照する通常共有は、所有者・受信者とも作品ドキュメントの方式を用いる。
- `scripts/test-text-reading.cjs` / `scripts/text-reading-legacy-baseline.json`: 合成例、既存4作品の段落・読書単位の全内容ハッシュ、共有個人コピーの方式と進行、マップのリアクション位置を検証。作品本文は追加していない。

読み込み方式を作品ごとに保存し、既存作品の方式を変更しないため、旧作品の読書単位番号・保存進行は従来通り。共有者は同じ方式を認識できる版のReTAを使う必要がある。旧版クライアントは新フィールドを無視して従来整形するため、新方式の作品で位置が一致しない。

## 検証結果

`node scripts/test-text-reading.cjs <ローカルの校正済みTXTパス>`で対象作品を検証。引数を省略した場合も合成例・既存作品・共有コピー・マップの検証を実行する。

- 対象TXT：タイトル・著者の2行を除き634段落。章見出しⅠ〜Ⅶ、端書き、後記を独立して保持。
- 本文の全文字列・順序・空白が入力と一致。ルビ制御記号・傍訳とタイトル・著者を除く本文は101,563コードポイント。元HTML由来のタイトル11文字を含める従前の数え方では101,574。
- ルビ2件は親文字の空白を含め、既存変換関数で正しいruby/rtになる。
- 読書単位は1,415。各段落の表示単位を再連結すると元段落と完全一致し、再読込しても単位の内容・番号が一致。先頭末尾の空白、句点後の空白にも合成例で対応確認。
- 従来作品の段落数／表示単位数：だしの取り方15／33、白昼夢50／78、In The Megachurch 938／1,043、吾輩は猫である2,188／5,227。変更前の段落・表示単位のJSONハッシュとすべて一致。
- 共有の個人コピーはproofread-v1／未指定legacyの両方をモックトランザクションで確認。保存済み進行の番号・表示単位数・しおりが保持される。
- リアクションとReTAロードのマップは同じ読書単位番号を利用する既存処理を維持。リアクションの番号別集約・未到達位置の非表示を実際の関数で確認。
- `npx tsc --noEmit`、`git diff --check`成功。
- 指定の`npm run build`は実行したが、既存Google Fontsの外部取得に失敗。Nextのテスト用環境変数`NEXT_FONT_GOOGLE_MOCKED_RESPONSES`とインストール済みGeistフォントを使用したTurbopack再試行も、この環境のポート利用制限で失敗。
- 同じ一時フォント設定で`npm run build -- --webpack`は成功。コンパイル・TypeScript・静的ページ生成を完了。ソースのフォント設定やビルドスクリプトは変更していない。一時設定は/tmpにのみ保存し、リポジトリへ追加していない。

## 未実施・制限

ブラウザ上の実表示、Firebase実接続での保存・復元、複数端末での共有読み、リアクション送信の実機試験は未実施。機能の統合経路はソース確認とローカルテストで検証した。進行データの自動移行、登録済み作品の方式変更機能、旧版クライアントとの新方式共有は今回の対象外。

対象の本文TXT・HTMLは変更せず、リポジトリへコピーしていない。元から存在した未追跡ファイルには触れていない。初回実装時点ではコミット・push・デプロイ・クラウドデータ変更は行っていない。

## 縦書きの半角数字

表示時だけASCII数字1文字ごとにspanを付け、1em四方のinline-block内で正立・中央揃えにする。vertical-alignはbaselineとし、縦書き親要素の中央ベースラインに合わせる。通常縦書きと2文グループの描画でのみ有効。横書き、原文、段落・読書単位番号、保存済み進行、リアクションのデータは変更しない。タグ・属性・HTML文字参照を表示用の置換から除外する。

`node scripts/test-vertical-digits.cjs`で半角数字だけの装飾、複数桁、1文字1em、ルビ・辞書・横書きの維持、両縦書き描画経路を検証する。書籍本文はテストへ含めていない。
