# グループ内TXT作品共有

## 原因と設計

TXT追加は毎回text_UUIDを発行するため、同じ本文でも異なる作品になっていた。
作品を開く処理もownerIdがログインUIDと一致することを要求していた。
参加者・リアクションは既存のgroupId/workIdによって表示を選別している。

今回、本文は既存works文書1件を維持し、groupId/workId単位の参照を保存する。
同じ共有文書は作成のみ許可し、再共有はトランザクションで既存文書を確認して何もしない。
所有者だけが共有可能。受信者が所有者を偽装して再共有することはできない。
同じ本文を以前それぞれアップロードした作品は自動統合しない。全員が共有一覧の同じ作品を開く。

## データ

- `works/{workId}`: 既存TXT本文。workId/type/title/author/rawText/ownerId等は維持。
- `groupWorkShares/{groupId}/works/{workId}`: workId, type:text, title, author, ownerId,
  sharedBy, sharedByName, sharedAt（Unixミリ秒）。本文・読書位置は含めない。
- `sharedWorkAccess/{uid}/works/{workId}`: groupIdのみ。
  本人が明示的に作品を開く際に作成する参照。作品数とグループ数の積をworksへ埋め込まないための文書。
  参照が残っても、Rulesが所属と共有文書を毎回検証するため、未保存作品は退出後のサーバー読取りを拒否。
- `groupSharingAccess/config`: enabled:boolean。管理者だけがConsoleで設定。
- `groupInvites/{参加コード}`: groupIdのみ。コードを知る人の単件getのみ許可、一覧取得禁止。
- `groupJoinAccess/{uid}/groups/{groupId}`: codeのみ。
  正しい招待コードを確認した本人が作成。自分をグループに追加するための参照。

`readingProgress/{uid}_{workId}`、participants、reactions、bookmarks、読書イベントの保存方式は維持。
グループ参加の操作は従来のコード入力のまま。共有機能有効時だけ招待索引を使う。
グループの30秒の非アクティブ判定と最大3人を維持。

## 通知とオープン

Firestore onSnapshotで共有参照を購読し、画面下にコンパクトな通知を表示する。
スマホでは既存下部メニューの上、PCでは右下。本文DOMは追加・複製しない。
通知受信・一覧更新では作品・位置・モード・スクロールを変更しない。
「この作品を開く」または一覧「開く」の操作だけで既存TXT選択handlerを呼ぶ。
本文取得前に共有先・workId/type/ownerIdを検証する。
現在位置は既存saveReadingProgressで保存し、次の作品は本人のuid/workIdで復元、初読なら文頭。
共有者の位置は参照しない。readerModeは強制変更しない。共有表示は既存「一緒に読む」を使う。

「あとで」は通知だけを閉じ、共有一覧には残す。通知の既読はuid/groupId別localStorageに保存。
別端末で同じ通知が再表示されることはあるが、共有文書が重複して増えることはない。
複数作品は一覧にすべて残り、未確認通知は最新から1件ずつ表示する。
共有者ログアウト後も作品と参照は残る。削除済み作品はオープン時に明示的にエラーにする。
ネットワーク復帰時は購読が追随する。共有本文を開くときはサーバー確認を必須にする。
グループの所属喪失を検知した場合は通知・一覧を消し、既存グループ選択画面へ戻る。

## Rulesと本番設定（未実施）

`firestore-group-work-sharing.rules` は、前回提示・公開報告のあったフレンド用Rulesを土台とする全体置換案。
2026-10-09にFirebase Rules APIから公開済みFirestore Rulesを読み取り取得した。
初回取得時は前回のフレンド用Rulesと一致。その後、利用者による共有用Rules公開後の最終確認で、
コメント・空白を除いた内容が個人保存追加前のRules案と一致することを確認済み。
今回追加したsavedSharedWorksのRulesも、デモ公開前のFirebase Rules APIによる読み取り確認で公開済みRulesとの一致を確認した。
取得のみで公開・変更はしていない。公開直前にも独自変更が増えていないか確認する。
新しい許可を追加するだけでは包括allowから迂回できるため、対象コレクションを包括allowから除外。
worksのTXTは所有者、有効な共有参照を持つ現所属メンバー、または明示的な個人保存の本人だけが取得可能。
所有者以外は本文更新・削除・ownerId変更不可。非公開TXTをurl/presetへ変更して公開することも不可。
共有参照は所属グループだけが取得できる。受信者は退出後、通常のアクセス参照だけでは本文取得不可。
明示的な個人保存をした作品には退出後も閲覧権限を維持する。
所有者自身の個人作品を読む権限は、退出後も維持する。
グループ所属の偽装、他人の追加、生存中の他人の除外、将来のheartbeat時刻の偽装を禁止。
共有有効時はグループ／招待索引の全件列挙を禁止し、コード入力の本人加入を許可。
フレンド用Rulesは維持。その他のコレクションの包括的な旧権限は今回の案では維持する。

安全な設定順：

1. 現行Rulesを控え、本案と差分を確認する。独自変更があれば本案で上書きしない。
2. 新UIをローカルで確認する。本番クライアントは未更新のため、この段階でenabled:trueにしない。
3. 管理者が既存groupsの各ドキュメントIDとcodeを確認し、
   `groupInvites/{code}` に `{groupId: "そのグループのドキュメントID"}` を準備する。
   groupsの本文・招待コード・所属・既存作品は変更しない。重複codeがあれば有効化前に対応を検討する。
4. ローカル検証・レビュー後に専用RulesをConsoleで公開する。
5. 新クライアントを公開する承認が得られた後、更新を反映する。
6. 管理者が `groupSharingAccess/config` に `enabled: true`（boolean）を設定する。
7. 新しいクライアントで2～3アカウントの実機確認を行う。

本作業では本番設定・本番データ・Rules公開・commit/push/deployは一切行っていない。
firebase.json/.firebaserc/functionsやバックアップは変更していない。
新ライブラリとFirestore複合インデックスは不要。索引未準備の既存グループには有効化後新規参加できないので注意。

退出で禁止できるのは以後のサーバー取得。すでに読んだ本文やブラウザキャッシュのコピーを遠隔消去する機能ではない。

## 明示的な個人保存（2026-10-09追加）

共有一覧の「マイライブラリに保存」は `savedSharedWorks/{uid}/works/{workId}` に
workId/title/author/ownerId/sourceGroupId/savedAt（ミリ秒）を保存する。
本文は複製せず、元のworkIdとownerIdを維持する。保存する時点で現所属と共有情報・本文メタデータをRulesで検証する。
本人だけが一覧・単件を読め、更新は禁止。所属外から新しい閲覧権限を作ることはできない。
明示保存済みの作品だけは、退出後や共有機能無効化後も元本文への閲覧権限を維持する。
保存せず「開く」だけの場合は従来どおり退出後に取得不可。
元所有者が本文を削除すると保存済みでも読めない。所有者変更や本文削除の権限は追加しない。

グループ未所属の選択画面にも保存一覧を表示する。
作品を押すと既存のTXTオープン・本人のuid/workIdによる読書位置復元を使用し、ひとり読み画面へ移る。
本文DOM・しおり・自動スクロール・レイアウト変更処理は共通。
グループ未所属では共有モードに変更できない。「グループ選択へ戻る」から加入できる。
保存操作だけでは現在の作品・読書位置を切り替えない。別端末でも本人の保存一覧を購読する。

デモ公開前に公開済みRulesを読み取り、今回のRules案とコメント・空白を除いて一致することを確認した。追加のRules公開は不要だった。
本作業では本番Rules・データを変更しない。
タブレット縦向きの色補正は640〜1024px・portrait・any-pointer:coarseに限定し、本文やレイアウトは変更しない。
